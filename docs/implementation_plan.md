# StuTrade 实施方案

## 项目形态

平台由**撮合引擎**和多个**业务宿主**组成。前后端分离；本目录是整个项目产品范围、架构和跨仓库契约的唯一文档真相源。业务后端保留在主仓库，撮合引擎和前端分别维护独立仓库，并通过 Git submodule 接入主仓库。

- **撮合引擎**：在 `engine` 子仓库处理买方需求、卖方供给、候选匹配和撮合请求。
- **业务宿主**：在主仓库代码中提供领域字段、领域匹配规则、用户入口、订单和履约流程。
- **前端应用**：在 `web` 子仓库实现页面、交互、浏览器测试以及前端构建和发布。
- **二手物品宿主**：处理物品、价格、成色、ISBN 等二手交易规则。
- **其他宿主**：最终接入校园跑腿和租赁。

这里的“文档真相源”只覆盖产品语义和跨组件边界，不替代实现所有权。engine 的导出 Go 代码与测试唯一负责其运行协议；宿主接受并与路由、DTO 同源的 OpenAPI 唯一负责 HTTP 结构；migrations 唯一负责 PostgreSQL schema；web 代码与测试唯一负责前端交互和发布。子仓库可以在 README 中解释自己的开发入口，但不得维护会与这些权威来源竞争的契约副本。

前端在宿主 API 尚未实现时维护的 OpenAPI 是并行开发提案。宿主接受或修订后，必须一次性把 schema 权威位置、前端生成输入、MSW 和漂移检查迁移到同一来源，不能让宿主与 web 长期各自维护一份 OpenAPI。

## 最终愿景

用户可以发布买方需求或卖方供给。系统根据双方条件发现可能的交易，并通知双方确认。用户也可以绕过自动撮合，直接对看到的需求或供给发起成交。

平台统一记录挂单、撮合请求、确认结果和履约状态。二手物品、跑腿和租赁共享撮合能力，各自保留领域规则。

直觉验收：

1. 买方发布“指定 ISBN 的二手书，最高价为 X”。
2. 卖方发布同一 ISBN 的二手书，价格为 Y。
3. 当 `Y ≤ X` 时，系统生成撮合 Request，通知双方；双方确认后成交，第一版按卖方价格成交。
4. 卖方可以看到买方需求，直接按买方价格接单。
5. 买方可以看到卖方供给，直接按卖方价格购买。
6. 成交后双方查看并推进订单，完成交付。

同理，二手物品交易可能不再比较 ISBN 码，跑腿也可能有更严格的时限要求，这些功能我们**最终**产品都应该支持。

## 第一版 MVP：二手书交易

先搭建引擎与业务层分开的最小骨架，定型项目结构，再迅速补全二手书交易的三条端到端路径：

- **自动撮合**：买方出价不低于卖方给价时，撮合引擎自动提出 Request；双方手动确认后成交。
- **卖方主动接单**：卖方查看买方需求，按买方出价成交。
- **买方主动购买**：买方查看卖方供给，按卖方价格成交。

第一版由引擎提供基本价格规则：`卖方给价 ≤ 买方出价`。自动撮合默认以卖方给价成交。撮合请求不等于成交，双方确认后才建立交易。

二手书宿主通过引擎定义的 Protocol 注入额外成交判断类或函数，例如 ISBN 必须一致、用户不能购买自己的书、书籍和需求必须仍然有效。引擎负责调用这些判断；最终版本也采用这一机制，不引入通用规则语言。

宿主同时提供最小用户系统和业务入口，使二手书交易的三条路径都能完成 E2E 测试。第一版不包含真实支付、聊天、物流、竞价和自由文本智能匹配。
