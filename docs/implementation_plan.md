# StuTrade 实施方案

本文只记录尚未完成的目标、实施顺序和验收条件。当前已经具备的入口以代码、测试和根 README 为准；产品定义见[项目说明](project-description.md)，责任分配见[责任与权威来源](governance/ownership.md)。

## 当前基线

当前仓库已经完成交付骨架：

- 后端支持 `serve`、`migrate up` 和 `version`，并实现 `develop`、`native`、`production` 三个 profile。
- PostgreSQL migration、sqlc、`/health`、`/ready`、Compose 和 native/production 构建入口已经建立。
- web 已提供 OpenAPI、生成的 TypeScript 类型、MSW、应用路由与壳层。
- engine 已提供 Amount、Listing、MatchRequest、价格兼容、状态转换和发布挂单用例。

尚未完成的是业务宿主纵切、engine 成交用例、真实 API handler、完整前端页面和跨仓库端到端验证。

## 目标领域模型

MVP 只实现完成当前用例所需的实体：

| 实体             | 所有者 | 目标职责                                       |
| ---------------- | ------ | ---------------------------------------------- |
| 用户与会话       | 宿主   | 注册、登录、退出和当前用户身份                 |
| 二手书与挂单资料 | 宿主   | ISBN、书名、作者、成色、备注及 Listing 关联    |
| Listing          | engine | 所有者、资源引用、买卖方向、价格、状态和时间   |
| MatchRequest     | engine | 参与方、相关 Listing、来源、成交价、确认和状态 |
| 订单             | 宿主   | 买卖双方、成交来源、成交价格和最小履约状态     |

宿主只保存当前业务特有的挂单或撮合资料，不复制 engine 已拥有的价格、方向、状态、确认等通用事实。两部分通过共享标识、不透明资源引用和适用的数据库外键关联；只有出现真实业务字段时才建立宿主扩展记录，不为 Listing 与 MatchRequest 强制建立对称空表。数据库列和 Go 字段只在对应纵切实施时确定，不为未来场景预留字段，也不增加通用 `Constants` 或 `Variables` 容器。

## 目标流程

### 发布与自动撮合

1. API 完成身份识别与结构校验，宿主校验 ISBN、书籍信息、金额和所有权。
2. 宿主在同一工作单元中保存二手书资料，并调用 engine 创建和持久化通用 Listing；宿主不直接构造或写入 engine 状态。随后显式触发一次同步自动撮合；engine 不运行后台轮询。
3. engine 获取候选并按价格、创建时间和 ID 稳定排序，再调用宿主规则检查 ISBN、自买限制和资源有效性。
4. engine 在工作单元内稳定加锁、重做成交前检查、预留双方 Listing，并创建唯一 pending MatchRequest。
5. 并发或重复扫描同一组合时返回稳定的已有结果或冲突，不提前创建订单。

候选发现只用于缩小范围；决定正确性的状态和规则必须在写事务中重新检查。

### 双方确认

1. 宿主保证当前用户只能操作自己参与的 MatchRequest。
2. engine 在工作单元内锁定请求和关联 Listing，幂等记录当前一方确认。
3. 第一方确认后请求保持 pending；第二方确认时重新执行宿主规则。
4. 规则仍成立时，在同一事务中完成 MatchRequest 和 Listing，并创建唯一宿主订单。

### 主动成交

- 卖方接受需求时按买方报价成交，并提交或选择实际交付的二手书资源。
- 买方购买供给时按卖方报价成交，只需要买方身份和目标供给。
- 两条路径复用相同的身份、有效性、自买和原子写入规则。
- engine 创建 completed MatchRequest 和订单引用，不要求发起方制造没有产品含义的反向 Listing。

### 拒绝与撤回

- 任一参与方可以拒绝 pending MatchRequest；仍有效的双方 Listing 恢复为 open。
- 发布者可以撤回 open Listing；撤回 reserved Listing 时取消关联请求并释放有效的对手 Listing。
- completed MatchRequest 和已建立订单不通过撤回挂单回滚。
- 拒绝、重复拒绝、撤回和确认并发时只能产生一个稳定终态。

## 数据与事务计划

首批业务 migration 覆盖用户与会话、二手书资料、engine 通用 Listing、MatchRequest 和订单。主仓库继续拥有物理 migration 与查询文本；engine 拥有通用状态的命令、查询、恢复语义和逻辑持久化 Protocol。结构性规则优先由 PostgreSQL 的外键、唯一约束、检查约束和状态组合约束保证。

宿主数据库适配器将负责：

- 将 sqlc 行转换为 engine Protocol 的持久化表示，并由 engine 负责合法恢复；
- PostgreSQL 错误到稳定领域错误的翻译；
- 实现 engine 按当前用例声明的小型存取 Protocol；
- 按 Listing ID 稳定加锁的工作单元；
- 宿主二手书资料、engine 状态和宿主订单之间的外键与原子协作；
- 以 MatchRequest ID 唯一约束订单，防止重试重复创建。

宿主业务代码通过 engine 的公开命令和查询取得通用状态，再按 Listing ID 或资源引用批量取得二手书、用户和订单资料，组装业务对象与 HTTP DTO。ISBN、书名或成色搜索先在宿主资料中确定候选标识，再通过 engine 的批量读取取得权威通用状态，避免逐项读取。只服务展示的联合投影不得被用于恢复或修改 engine 实体。

重点并发场景包括两个买方争抢同一供给、自动撮合与主动购买竞争、双方同时最终确认、确认与拒绝或撤回竞争，以及重复提交直接成交。

## HTTP 与前端计划

业务 API 使用 `/api/v1`，并由 `web/openapi/stu-trade.yaml` 生成前端传输类型和后端 Gin strict 接口。业务 handler 必须通过生成接口注册；不存在的路径返回后端 404，不回退到前端页面。

计划实现的纵切包括：

- 本地账户、密码哈希和 `HttpOnly`、`SameSite` 会话 Cookie；
- 出售与求购挂单的发布、浏览、详情和撤回；
- 按 ISBN 或书名搜索，并按买卖方向与成色筛选；
- 自动撮合列表、双方确认与拒绝；
- 主动接单、主动购买、订单列表和履约确认；
- 加载、空状态、校验、鉴权、资源失效和并发冲突反馈。

MVP 不要求书籍封面。前端只展示和提交状态，不复制宿主拥有的 ISBN、自买、有效性、幂等和并发规则。

## 交付阶段

阶段按可演示结果推进，不以空目录或形式化 CRUD 作为完成标准：

1. **账户与挂单纵切**：两个用户能够登录并发布、浏览和关闭自己的需求或供给。
2. **主动购买纵切**：买方能够直接购买供给，按卖方报价创建 completed MatchRequest 和唯一订单。
3. **主动接单纵切**：卖方提交实际书籍接受需求，按买方报价成交，并复用主动购买核心。
4. **自动撮合纵切**：发布相容挂单后产生 pending MatchRequest，双方确认后只建立一笔订单。
5. **履约与交付**：双方查看订单并完成最小履约，验证三种部署配置。

每个阶段同时交付所需 migration、查询、生成代码、API、宿主测试和前端交互。MVP 完成标准是集成环境可演示三条核心路径，关键竞争场景有自动化回归，并能从同一后端提交构建 Linux 服务和 Windows 本机版。

## 目标目录

目录只在对应纵切产生真实代码时建立：

```text
stu-trade/
|-- cmd/stu-trade/       serve、migrate、version
|-- internal/
|   |-- app/             配置、依赖装配和进程生命周期
|   |-- httpapi/         Gin、生成接口与传输映射
|   |-- user/            用户与会话
|   |-- listing/         二手书资料、市集、发布与业务对象组装
|   |-- trade/           订单与履约
|   |-- matching/        宿主规则与 engine 类型适配
|   |-- db/              sqlc、engine Protocol 与事务适配
|   `-- testutil/        真实测试资源辅助
|-- migrations/
|-- queries/
|-- engine/
`-- web/
```

MVP 保持一个宿主进程。后续领域优先作为独立模块接入同一引擎，只有出现明确的独立部署需求时才重新评估进程边界。
